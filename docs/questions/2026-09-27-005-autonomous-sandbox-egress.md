## 背景与证据

用户要求每个沙箱在自己的 Pi Web 中独立配置模型，不通过控制平面模型连接。现有沙箱位于 Docker internal 网络，只能访问控制域代理；要直接调用沙箱中配置的外部模型，必须改变出站网络。Pi 官方安全文档指出，沙箱内 Pi 工具或其子进程可以读取该容器可见的凭据并使用其网络权限。是否允许直连以及允许何种代码，决定网络、安全和模型密钥边界，不能由旧代理方案自动继承。

### SBX-005：首版自主沙箱的出站与信任范围

1. **本地可信内部使用，沙箱直接出站（建议）**：每个沙箱独立 Docker 网络，可访问用户在 Pi Web 中配置的模型端点；控制平面不接触供应商凭据或模型请求。沙箱内代码/工具也可能读取其凭据并访问公网，首版不用于不可信代码或公开多租户。
2. **受限出站**：仍由沙箱自行保存凭据，但通过独立网络策略限制可访问的目标；需要定义谁维护目标清单、如何处理 DNS/动态地址和依赖下载，启动速度与兼容性会受到影响。
3. **暂不允许外部出站**：仅接本地可达模型；实现最简单，但无法达到“沙箱内自行配置第三方模型”的常见使用方式。
4. **其他，请说明。**

建议选择 1 作为本地首版，以匹配独立配置和快速启动；如果需要运行来源不可信的代码或允许多人远程访问，应先选择 2 并补充隔离设计。

回答区：1 我认为docker环境就是足够隔离了吧？会有风险吗？

结论（2026-09-27）：选择方案 1，本地可信内部使用，沙箱直接出站，各自持久化模型配置和凭据；此回复解除实施阻塞。Docker 隔离文件、进程与权限，但仍共享宿主内核；容器内 Pi 工具可读取自己的凭据并使用网络，Docker 管理员也可访问容器数据。实施保留非 root、无 Docker socket、只读根、资源限制和回环密码入口；不能据此宣称抵御不可信代码或公开多租户。用户关于风险的询问已在本结论和对话中解释，不另设重复确认。

## 影响

答案决定新沙箱 Docker 网络、Pi Web 模型连接能否工作、凭据泄露范围及端到端验收环境。未回答前，产品代码不实施出站网络和自主模型配置；资源收口、历史状态标注和迁移设计可继续。
