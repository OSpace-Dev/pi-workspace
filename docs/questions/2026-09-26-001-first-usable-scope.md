## 用户原始目标

项目以 `refer/pi-main-0.87.1` 为当前设计和开发基线。用户希望通过 Web 工作空间快速创建服务器上的沙箱，在其中启动 Pi Agent 完成指定任务；提供企业级管理与实时运行界面；允许系统提供或用户定制 Agent（包括 Skill、外部资料）；并考虑 Web 与即时通讯软件交互。沙箱技术和首版边界尚未确定。

## 已核实的技术事实

- 参考目录的 `packages/coding-agent/package.json` 标注包名 `@earendil-works/pi-coding-agent`、版本 `0.87.1`、MIT 许可；目录根 `LICENSE` 也是 MIT。当前仅核对了本地副本的声明，未核对来源真实性及所有第三方依赖的许可。
- [SDK](../../refer/pi-main-0.87.1/packages/coding-agent/docs/sdk.md) 可在 Node.js 或 Bun 进程创建会话、配置工具与资源、订阅运行事件。[RPC](../../refer/pi-main-0.87.1/packages/coding-agent/docs/rpc.md) 可通过长驻子进程收发命令与事件，其扩展 UI 只支持部分交互，见 [RPC Extension UI](../../refer/pi-main-0.87.1/packages/coding-agent/docs/rpc-extension-ui.md)。
- [Skill](../../refer/pi-main-0.87.1/packages/coding-agent/docs/skills.md) 可以按路径加载；SDK 资源加载器支持附加 Skill 路径与过滤，见 [示例](../../refer/pi-main-0.87.1/packages/coding-agent/examples/sdk/04-skills.ts)。外部资料如何进入任务上下文仍需定义。
- 内置 `read` 工具明确支持文本和常见图片，见 [实现](../../refer/pi-main-0.87.1/packages/coding-agent/src/core/tools/read.ts)；PDF、DOCX 等文档应另行设计解析与校验流程，不能假定 Pi 已内置完整文档处理能力。
- [容器化说明](../../refer/pi-main-0.87.1/packages/coding-agent/docs/containerization.md) 明确支持把完整 Pi 进程放入 Docker，同时指出凭据、挂载和网络访问仍须收紧。[安全说明](../../refer/pi-main-0.87.1/packages/coding-agent/docs/security.md) 提醒 Pi 工具按进程权限执行，项目信任机制不能替代隔离。
- [pi-server](../../refer/pi-main-0.87.1/packages/server/README.md) 明确标为实验性本地服务，其传输不内置对等端认证；[pi-client](../../refer/pi-main-0.87.1/packages/client/README.md) 是实验协议客户端。当前参考目录未发现可直接部署的企业级 Web 管理台。若“Pi 的 Web 插件”指目录外组件，需取得其名称和来源再评估。

## 暂定理解与可行性

候选用户流程：选择任务与 Agent 配置 → 创建隔离工作目录和运行环境 → 启动 Pi → Web 查看流式消息、工具调用与任务状态 → 处理必要的用户输入 → 查看结果与产物 → 停止或恢复任务。此流程是建议，不代表已确认需求。

基于上述接口，做服务器端集成可行。首轮技术验证可比较“容器内 Pi RPC，由 Workspace 服务桥接事件”与“容器内 SDK 工作进程”；这只是待验证路线，不构成技术选型。管理台、身份权限、任务调度、持久化、审计、IM 适配和沙箱策略需要 Workspace 实现。即时通讯能否承担审批、附件和复杂工具交互，取决于所选平台及安全要求。

## 本轮结论

首个可用版本服务内部团队，优先验证文档与资料处理场景。即时通讯在首版中只承担通知与结果链接，完整任务交互由 Web 承担。这是用户已确认的范围方向，不代表文档任务、权限、界面、沙箱或集成技术已经确定。
