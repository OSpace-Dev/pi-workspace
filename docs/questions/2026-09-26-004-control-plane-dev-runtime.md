# 控制平面的本地开发运行方式

- 日期：2026-09-26
- 状态：CP-001～002 已回复；本地服务拓扑和 Engine 访问方式已确认
- 决策人：项目发起人（运行约束）；技术方案待架构评审
- 关联：[初始 Product Backlog](../planning/2026-09-26-001-initial-backlog.md)、[沙箱隔离边界](2026-09-26-003-sandbox-isolation.md)

## 已确认的偏好与事实

- 用户只有一个 WSL Ubuntu，希望管理后台也在其中运行，并优先使用 Docker 进行开发和调试，避免把后台的运行时、依赖与服务安装到 WSL 主机。
- 项目自有代码位于 `codes/`，目前该目录为空。当前 Pi Web 容器只是交互体验环境，不能替代正式控制平面。
- 本地 WSL 的 Docker Engine 和 Docker Compose 已可运行；本记录不指定生产部署方式。

## 候选开发边界

控制平面的 Web、API、数据库和其他服务可作为独立容器按需启动；开发依赖由镜像和命名卷承载。源码保留在 `codes/`，由开发容器挂载或在镜像构建时复制。具体技术栈、模块边界、端口和数据模型仍待需求与架构设计。

管理服务若需创建和停止任务容器，访问 Docker Engine 的组件拥有很高的宿主权限。待比较：由单独的受限运行代理执行容器操作，或其他可审计的编排接口；不应把 Docker socket 直接暴露给浏览器侧或所有后台服务。任务沙箱与控制平面应分开管理。

Windows 工作区经 WSL 挂载到开发容器时，文件监听与 I/O 性能需实测。若影响热重载，再决定是否采用 WSL 内工作副本或其他同步方式；不能假定现有挂载在所有技术栈下都足够快。

## 待设计与验证

1. 用选定技术栈验证一条容器化开发命令能启动、查看日志、重建和停止控制平面，WSL 主机无需安装该技术栈的全局依赖。
2. 验证 `codes/` 源码挂载后的热重载、权限与性能；记录可复现命令和限制。
3. 明确控制平面与任务沙箱的网络、数据卷和 Docker Engine 访问边界；比较受限运行代理与其他方案的权限及运维成本。

结论需在架构设计中确认，再把开发环境任务设为 Ready 并实施。

## 2026-09-27：最小运行拓扑决策

背景：项目发起人已要求控制平面使用数据库，模型连接在管理界面配置，真实上游凭据由控制域代理持有；见[模型接入回答](2026-09-27-001-model-access.md)。[架构草案](../architecture/2026-09-27-001-local-workspace.md)已划分 Web/API、模型代理、运行代理、任务容器和持久化数据库。此处记录本地首轮的技术组合。决策人为项目发起人，原选项与回答保留作追溯。

### CP-001：首轮控制平面的服务与数据库方案

1. TypeScript/Node API + 独立模型代理 + 独立 Docker 运行代理 + PostgreSQL 容器（建议）：与 Pi/Node 生态接近，模型密钥及 Engine 权限分处不同服务；数据库可支持后续多任务并发。首轮需维护较多容器，Web 前端框架在界面设计时选定。
2. TypeScript/Node API 内合并模型代理 + 独立 Docker 运行代理 + SQLite 卷：服务更少；API 和上游密钥共进程，后续并发与权限拆分成本较高。
3. 其他，请说明。

回答区：1

结论（2026-09-27）：采用 TypeScript/Node API、独立模型代理、独立 Docker 运行代理和 PostgreSQL 容器。Web 前端框架待界面设计；各服务按交付顺序逐步实现，不要求首个开发环境任务预建空服务。

影响：`codes/` 模块边界、Compose 服务、数据库迁移与备份、代理隔离、构建和调试命令。选项 1 的模型代理和运行代理仍需仅在私有 Docker 网络提供受控接口，不发布到 Windows 端口。

### CP-002：本地运行代理如何访问 Docker Engine？

1. 专用运行代理容器独占挂载 Docker socket（建议用于仅本机合成资料验证）：Web、API、模型代理和任务容器均无 socket；代理只接受带任务身份的固定创建/启动/停止/删除操作。代理被攻破仍可能获得宿主级 Docker 权限，需要严格限制入口并记录审计。
2. WSL 主机上运行独立守护进程访问 Engine：避免 socket 挂到容器，但违背“不污染 WSL 主机”的开发偏好，并增加主机服务管理。
3. 其他，请说明。

回答区：1

结论（2026-09-27）：本地单人合成资料验证由专用运行代理容器独占挂载 Docker socket；Web、API、模型代理和任务容器均不持有 socket。此方式仍给运行代理宿主级潜在权限，需限定可操作的容器与卷并验证；不能将此本地选择直接推广到多人或不可信代码环境。

影响：宿主风险、服务部署、故障处理和权限边界。未来多人或不可信代码任务需要重新评估此本地方案。
